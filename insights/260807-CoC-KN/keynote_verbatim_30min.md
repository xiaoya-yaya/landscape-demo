## 01｜开场（0:00—0:35）

大家好。

今天想和大家聊一件看起来很新、其实也很熟悉的事：Agentic AI 发展得这么快，开放生态靠什么跟上？

## 03｜图一直在变，什么值得留下（1:05—1:50）

[画面：只有问题。]

做 Agentic AI landscape 有一个很直接的困难：今天刚画完，明天就可能过时。

Stars 很高，未必还在维护；增长很快，可能只是一次发布带来的短期热度；两个项目写着不同的名字，解决的却是同一件事。要是只追热点，这张图很快就会变成越来越长的名单。

[下一步，答案卡出现。]

所以我们的取舍标准很明确：别人能不能接住它，继续往下做。

这里的“接住”包括很多层。代码能不能运行，接口能不能连接，许可证给了什么权利，模型材料够不够研究，贡献者有没有进入社区的入口。带着这个问题，我们来看四张图。

## 04｜Agent Infra：代码仍是入口，个人 Agent 与上下文同时升温（1:50—3:25）

[画面：Agent Infra 全景图。]

第一张是 Agent Infra。当前入图 74 个项目，按 Agent 从开发、运行到治理所需的能力划分。

先看整体结构。项目最多的两块仍然和 coding 直接相关：Agentic coding 有 12 个，Code-first frameworks 有 10 个。开发者最容易从代码进入 Agent，工具链也最成熟，所以这一带最拥挤。

[下一步，聚焦 Coding，洞察卡出现。]

不过，数量最多不代表变化最快。很多 coding 项目正在吸收相近能力，差异逐渐转向执行环境、上下文管理和团队工作流。看这一块时，我会同时问：它只是多包了一层模型调用，还是形成了可复用的工程边界？

[下一步，聚焦 Personal AI assistants。]

再看社区热度。74 个项目里，七月 OpenRank 排名前两位的都是 Personal AI assistants：OpenClaw 是 462.71，Hermes Agent 是 350.21。这一栏共有七个项目，其中五个是在 2025 年 7 月以后出现的。

代码仍是项目最密集的入口，个人 Agent 已经成为另一处很强的注意力中心。它们长期运行，也持续积累用户习惯和任务经验，memory 与 skills 很快会碰到管理问题。

[下一步，聚焦 Memory, knowledge & context。]

这正好解释了上下文层的变化。OpenViking 的月度 OpenRank 从三月的 112.46 上升到七月的 177.61。它把 memory、RAG 和 skills 收进 context database，让存储、检索和更新能够单独演进。

一个 Agent 如果只运行一次，prompt 可能够用；长期运行以后，谁能写入、什么应该保留、什么时候失效，都会成为工程问题。

[下一步。]

## 05｜Model Infra：Gateway、Serving 与许可一起变化（3:25—5:05）

[画面：Model Infra 全景图。]

第二张图看 Model Infra，共 58 个项目。它覆盖数据、训练、对齐、推理、网关和评测。模型能力最终能不能稳定交付，很大程度取决于这一层。

这轮更新里，我想讲三个不同的变化。

[下一步，聚焦 Model API gateways。]

第一是 gateway。OmniRoute 的月度 OpenRank 从二月的 4.48 上升到七月的 31.92。最初的人工短名单漏掉了它，增长信号让我们重新复核。

增长只能说明它值得重新检查，功能结论还要回到项目近期做了什么。

我们对照了三个项目的官方 release。LiteLLM 增加 MCP OAuth、工具列表与调用管理；AgentGateway 1.1 把 MCP 鉴权放进流量策略，同时覆盖 A2A 与 LLM 流量；ContextForge 1.0 增加 A2A runtime 和 MCP proxy security。OmniRoute 自己则把配额感知 fallback、MCP 与 A2A 放在同一个入口。

这组变化能支持的判断比较具体：同叫 gateway，项目处理的流量和治理对象已经不同。分类时要看实际功能，不能只看名字。

[下一步，聚焦 Serving · Inference。]

第二是 serving 内部开始分工。这个区从 6 个项目增加到 8 个。LMCache 处理 KV cache 复用，vLLM-Omni 处理多模态 serving。Agent 请求往往更长，重复前缀更多，执行链也更容易中断。缓存、调度、恢复逐渐成为独立产品边界。

[下一步，恢复全图，许可洞察出现。]

第三是许可证。58 个项目里有 39 个采用 Apache-2.0，大约三分之二。Model Infra 经常同时涉及硬件适配、专利授权和多家公司协作，Apache-2.0 在这一层的优势很明显。

这里再提醒一句：OpenRank 表示开源协作活跃度，不是模型性能或产品质量排名。

[下一步。]

## 06｜Large Models：使用、能力与开放程度没有排成一列（5:05—6:15）

[画面：Large Models 全图。]

第三张图把观察对象换成模型 endpoint。GitHub 活跃度不适合回答“模型有没有被真实使用”，所以这里合并 OpenRouter 和 ZenMux 在 2026 年 7 月完整自然月的数据，再用 Hugging Face 核验官方权重。

样本一共 50 个 endpoint：20 个提供公开权重，30 个没有公开权重。开放权重仍占重要位置，但没有占据多数。

[下一步，自动筛选 Top 10。]

先看真实使用前十。4 个提供开放权重，6 个没有公开权重。这个结果只能代表两个平台、这个月份和这组样本，但它至少说明，开放权重模型已经进入主流使用区，也出现在真实使用的头部位置。

[下一步，切到开放权重视角。]

再按能力类型看，分布很不一样。Reasoning 区 10 个模型里有 9 个开放权重；Frontier Generalist 的 13 个模型则都没有公开权重。不同能力路线在训练成本、数据风险和产品化方式上有自己的选择，不能用一个“开放率”概括全部。

[下一步，切到 AAI 可比样本。]

最后看使用和能力。最新 AAI 快照与 7 月使用 Top 50 匹配后，我们保留 AAI 前 10。GLM 5.2 在使用榜排第一，AAI 是 51.1；Claude Opus 5 的 AAI 最高，为 60.7，使用排名是第 23。

榜单回答的是特定能力，采用还会受到价格、延迟、部署方式和渠道影响。能力评测与真实选择应当并排看，不能互相替代。

[下一步，进入 ZenMux 价格与使用视角。]

## 09｜Awesome：知识资产开始直接面向 Agent（7:05—8:25）

[画面：Awesome 全图。]

四列按使用方式排列。发现是从清单找到项目入口；复用是把现成材料带进任务；安装提供命令或配置；运行则把团队的工作约定交给 Agent 持续执行。

前三张图看软件项目和模型。这一张看 instructions、skills、prompts、templates 和工作流。

这些仓库不一定运行一个服务，也可能没有很多代码。它们保存的是做事的方法：按什么顺序执行，哪些条件不能越过，结果怎样检查。过去这些经验主要写给人看，现在其中一部分开始直接交给 Agent。

[下一步，打开 AGENT-READY。]

26 个入图项目里，有 19 个已经提供 Agent 可以直接读取的材料。我们的判断依据很朴素：仓库里是否真的有 skill、instruction、hook、workflow 或 MCP 配置，而不是 README 里出现了 “agent-ready” 这个词。

[下一步，聚焦“安装”。]

这里的“安装”是我们按使用路径划出的“安装或注册工具”，direct 表示仓库给出了 Agent 可直接调用的命令、manifest 或配置。这个组有 7 个项目，7 个都满足。它只说明入口可以被机器执行，不代表项目质量或成熟度更高。

[下一步，恢复全图。]

还有一个时间信号：26 个项目里有 22 个创建于 2025 年以后。这是编辑样本的年龄结构，不能外推到整个 GitHub。它告诉我们，Agent-native 知识资产形成得很快，格式、分发和维护方式还远没有稳定。

[下一步。]

## 10｜四张图怎样形成这次观察（8:25—9:45）

[画面：四张图的数据源、时间窗和样本。]

讲完四张图，我想把方法说清楚。

它们没有共用一个排行榜。Agent Infra 和 Model Infra 的统计单位是 GitHub 仓库，主要看协作信号和技术位置；Large Models 的单位是平台 endpoint，看完整月份里的实际使用；Awesome 的单位是编辑样本，还要逐个阅读仓库材料。

所以，74 个项目、58 个项目、50 个 endpoint 和 26 个知识资产不能直接相加。它们回答的是四个问题。

[下一步，四行筛选路径展开。]

基础设施项目会复核仓库状态、README、近期活跃，以及它有没有补上结构里的空位。模型 endpoint 先在各平台内部计算分位，避免把两家平台口径不同的 token 数直接相加，再核验官方权重。Awesome 还要确认材料能否被 Agent 直接消费，并按获取、安装、创建和分发四个阶段归类。

[下一步，共同判断出现。]

四张图共享四条检查。第一，只比较完整时间窗；第二，仓库、endpoint 和知识资产分开统计；第三，使用、活跃、许可证和项目材料彼此校验；第四，编辑会补结构缺口，也会删掉重复表达。

这就是为什么我们没有把一串非常具体的漏斗数字放到台上。筛选过程可以复核，但观众此刻更需要知道数据从哪里来、为什么入图，以及这些指标能说明什么。

[下一步，观察、结论和行动出现。]

这轮观察留下三件事。开放权重已经进入主流使用区；协议、推理和可执行知识资产都在增厚；生态正在把过去隐含的工程经验写成公共接口。

采用数据告诉我们有没有人在用。许可证和发布材料决定社区拿到以后能做什么。

后续每次更新，我们会同步发布数据快照、处理脚本和入图理由。项目社区可以直接补证据、提修正。Landscape 也应当接受 review。

## 11｜Agent 跑起来以后，工程和开放开始变得具体（9:45—10:20）

[画面：深色转场，只显示标题。]

四张图讲的是变化。现在把视线往下移。

Agent 进入真实系统，会碰到一批软件工程里很熟悉的问题。

任务怎样编排，共享状态怎样在不同语言和系统之间传递，工具真的执行以后，失败怎样恢复，副作用怎样补偿。

这些问题长期存在。Agent 把更多步骤、更大权限和更长执行链放到了一起，于是它们同时变得紧迫。接下来回到 Apache。

## 12｜Apache 的规模来自持续发布和持续参与（10:20—11:45）

[画面：Apache、Projects 与 People。]

先看 Apache 的两个关键词：Projects 和 People。

在 Apache，代码是项目的产出，社区才是项目本身。一个项目能不能持续，并不只看仓库里还有多少 commit，也看有没有人承担发布、讨论、review 和治理。

[下一步，四组 FY2025 数据出现。]

ASF FY2025 年报列出 295 个 Projects、1,310 次 software releases、9,905 位 committers 和 1,147 位 members。

这四个数字口径不同，不能相加。项目数描述组织承载的社区；release 反映一年里的持续交付；committer 和 member 是不同层次的社区身份。

放在一起看，Apache 的规模来自一套长期协作能力：项目持续发布，贡献者因为持续、可信的工作获得更多责任，很多家公司和个人在同一套公共规则里合作。

[下一步。]

## 13｜Apache 在 Agentic 生态里的技术位置（11:45—14:00）

[画面：Apache Project Atlas，默认 Data, analytics & AI。]

如果只看 Agent UI 和框架，Apache 似乎离 Agent 热点有些远。把范围扩到数据、计算和运行系统，位置就清楚了。

左侧 7 个领域来自 Apache Projects Directory 的项目分类。同一项目可以属于多个分类，所以领域数量会重叠。这份目录由 Apache 官方维护。

右侧先看 Data, analytics and AI。Superset、ECharts、Airflow、Spark、Kafka 和 Flink 是这一领域关注度较高的项目。

[连续翻页，依次切换其余六个领域。]

再快速扫一遍另外六类。Libraries 里能看到 ECharts、Arrow 和 Thrift；Network 里有 Arrow、Thrift 和 Camel；Web 里是 Tomcat、CouchDB 这一组；Cloud & Operations 由 SkyWalking、JMeter、Maven 领头；Security 只有 4 个项目；IoT & Geospatial 里有 IoTDB 和 PLC4X。这里不用逐个读完，观众能看到每个分类都有对应项目。

下面一行始终保留进入 Landscape 的 6 个 Apache 项目。

Airflow 负责编排，Spark 负责分布式计算。Iceberg、Hudi 和 Paimon 处理数据表与持续更新，Gravitino 处理跨系统元数据。Paimon 和 Gravitino 在目录里缺少可用的项目分类，统计时没有塞进某个领域，入选结果仍然完整保留。

这一页的重点很简单：Agent 使用的很多数据与计算能力，已经由这些成熟的 Apache 项目承接。右侧的头部项目也提醒我们，Apache 的技术底盘远大于入图的这 6 个项目。

## 14｜Landscape 与蚂蚁参与的 Apache 项目怎样连起来（14:00—15:50）

[画面：Apache 与蚂蚁 Logo、三段运行链、全部项目卡。]

这一页把两个视角放在同一条运行链上。

左侧是进入 Agentic Landscape 的 6 个 Apache 项目，右侧是蚂蚁深度参与的 4 个 Apache 项目。项目卡上同时保留 Apache 和蚂蚁的标识，方便大家看清项目归属与参与关系。

这里不靠一张名单接另一张名单。我们沿着一次任务进入生产系统以后会经过的位置来讲。

[下一步，聚焦第一段：编排任务，完成计算。]

第一段是工作进入系统。Airflow 组织工作流和可追踪执行；Spark 完成大规模分布式计算；Celeborn 负责让 shuffle 与 spilled data 更稳定地流动。

Agent 发出任务只是一瞬间，真正的计算可能持续很久。编排、资源、数据移动任何一处不稳定，任务都可能停在中间。Celeborn 放在这里，连接了 landscape 里已经熟悉的编排与计算项目，也让蚂蚁参与的技术角色变得直观。

[下一步，聚焦第二段：共享数据、元数据与跨语言状态。]

第二段是状态变成共享资产。Iceberg、Hudi、Paimon 和 Gravitino 分别处理开放表格式、增量更新、流批统一的数据更新和统一元数据治理；Fory 处理高性能、多语言序列化。

Agent 系统经常由 Python、Java 和不同数据服务共同组成。上下文要跨进程流动，数据要有版本，元数据要能被发现。这里看到的是一套很具体的数据与状态平面。

[下一步，聚焦第三段：持续关系与失败恢复。]

第三段处理长期运行中最难躲开的两件事。GeaFlow 用流图计算维护持续变化的关系；Seata 处理跨服务事务、补偿和一致性。

一个 Agent 调用了三个系统，前两个成功、第三个失败，系统不能只回答“再试一次”。哪些动作可以重放，哪些要补偿，状态怎样对齐，都需要明确机制。

沿着这条链看，Apache landscape 和蚂蚁参与项目就自然接上了：它们共同覆盖计算、数据、状态和恢复，也对应 Agent 进入生产以后最先暴露的问题。

[下一步。]

## 15｜InclusionAI：开放生态有很多种入口（15:50—17:20）

[画面：InclusionAI Logo 与价值主张。]

Apache 展示的是跨组织基础设施怎样长期协作。接下来用 InclusionAI 看一套更靠近模型、Agent 和真实服务的技术栈。

“AI Built By Everyone, For Everyone” 里的 Everyone，可以落到很多具体角色。Available 是模型和工具能被拿到、理解和适配；Affordable 是使用成本足够低，能够进入真实服务；Inclusive 是开发者、领域专家和普通用户都能参与，也能分享技术带来的价值。

[下一步，GitHub、Hugging Face、ModelScope 三张卡出现。]

截至 2026 年 8 月 1 日，三个相关组织在 GitHub 有 93 个公开仓库；在 Hugging Face 有 198 个公开模型；在 ModelScope 有 188 个公开模型。

这三个数字不能相加。模型可能跨平台发布，GitHub 的 star、模型 Hub 的 download 和 like 也代表不同动作。它们共同说明，这套生态同时在交付软件和模型，而且已经形成跨平台的发布习惯。

## 16｜InclusionAI 的参与路径（17:20—20:20）

[画面：基础模型层。]

先看基础模型。Ling、Ring、LLaDA 和 Ming 分别关注语言、推理、扩散语言模型和全模态。

开放材料里除了权重，还有模型卡、阶段性 checkpoint、推理实现和评测。参与者可以复核评测、做领域适配，也可以研究量化、推理优化和模型行为。开放模型的贡献入口从这里开始变宽。

[下一步，切到具身大脑。]

第二层是具身智能。Robbyant 的 LingBot 系列把地图、深度、世界模型和动作模型连起来。

物理世界会给开放协作带来新的材料：空间数据、仿真环境、机器人适配、传感器差异和真实世界评测。对很多开发者来说，贡献并不需要重新训练一个基础模型，把环境和评测做扎实同样重要。

[下一步，切到 Model Infra。]

第三层是 Model Infra，这里可以多停一会儿。cuLA 和 Humming 做算子与系统组件；DLRover、ATorch 支撑预训练；AReaL、AReno 处理强化学习与 post-training；dInfer 和 dFactory 服务扩散语言模型的推理和微调。

这一层和前面的 Model Infra landscape 能直接对应。训练容错、弹性调度、checkpoint、RL 系统、推理效率，每一项都能形成独立贡献。没有大规模训练资源的开发者，也可以从算子、环境接口、任务集和可靠性进入。

[下一步，切到 Agent Infra。]

第四层是 Agent Infra。AWorld 组织工具、记忆、上下文与执行；AEnvironment 提供统一环境接口；Avernet 关注多 Agent 协同；ASearcher 把搜索任务和强化学习接起来。

这里能看到 landscape 分类在真实项目栈中的落点：runtime、environment、coordination 和 evaluation 逐渐成为清楚的工程边界。

[下一步，切到 AI Service。]

最上层是真实服务。LingGuang、金融服务和 AQ 连接具体用户。服务层一面展示能力，一面把长尾问题带回下面几层：模型哪里不稳定，环境缺什么接口，评测遗漏了什么场景，许可证和发布材料能否支持后续改进。

这张技术栈里，可以看到很多条可进入、可反馈、可持续贡献的路径。

## 17｜从软件走到模型，许可证要管的对象变多了（20:20—21:05）

[画面：标题，材料词尚未出现。]

讲到模型发布，我们要认真看一下“开放”这个词。

传统软件许可通常围绕源代码、目标代码、文档和衍生作品。模型发布可能同时包含权重、代码、数据说明、文档，甚至还要讨论输出。它们不一定由同一份条款覆盖。

[下一步，权重、代码、数据、文档、输出出现。]

所以看到“允许商用”或者“可以下载”，先不要急着给整个模型下结论。需要继续问：拿到了哪些对象，各自适用什么条款，研究和修改所需的材料有没有交付。

## 18｜三组许可证样本告诉了我们什么（21:05—22:35）

[画面：Agent Infra + Model Infra 的 132 个仓库。]

先看 landscape 里的软件项目。Agent Infra 和 Model Infra 合起来有 132 个仓库。其中 Apache-2.0 有 61 个，MIT 有 37 个，两者合计 74.2%。另有 25 个仓库的 GitHub SPDX 元数据是 NOASSERTION，其他许可证 9 个。

NOASSERTION 不能直接读成“没有许可证”。它只表示这次通过仓库元数据没有得到可确认的 SPDX 结论，还需要回到 LICENSE 文件和项目文档复核。

这组分布说明，宽松软件许可证仍然是 Agent 与 Model Infra 协作的主流工具。

[下一步，Hugging Face Top 100 模型仓库出现。]

再看 Hugging Face Text Generation 按下载量排序的 Top 100 模型仓库。Apache-2.0 有 57 个，MIT 有 19 个，合计 76%。剩下的 24 个仓库里，Llama 3 系列的三种 license tag 合计 8 个，Gemma 2 个，Apple AMLR 和 BLOOM RAIL 各 1 个；8 个标成 `other`，4 个没有 license tag。

`other` 只是 Hugging Face 模型卡里的标签，具体条款仍要逐个打开模型卡确认。没有 license tag 也不能直接读成没有许可证。

HF Top 100 的统计单位是仓库，不是独立模型家族；里面会有量化版、微调版和测试仓库。license tag 是发布者填写的元数据，也不能证明代码、训练数据和修改材料已经一起开放。

[下一步，调用量 Top 50 中的开放权重模型加入对照。]

前面那张 Large Models 图使用的是 2026 年 7 月 OpenRouter 和 ZenMux 调用量。两个平台各自转成月度 percentile，再做 50/50 合成。Top 50 里有 20 个模型找到了官方公开权重仓库。

这 20 个里，MIT 有 8 个，Apache-2.0 有 6 个，合计 70%。调用量综合排名前三的 GLM 5.2、DeepSeek V4 Pro 和 DeepSeek V4 Flash 全部使用 MIT。Apache-2.0 组里有 Step 3.7 Flash、HY3、gpt-oss-120b、两款 Gemma 4 和 Mistral Nemo。

另外 6 个更值得逐个看：Kimi K2.7 Code 和 Kimi K2.6 使用 Modified MIT；Kimi K3、MiniMax M3、HY3 preview 和 Nemotron 3 Super 各自使用模型专用或社区许可证。它们的商业使用、品牌和再分发条件并不相同。

调用量 Top 50 更接近头部模型，HF Top 100 提供一个更宽的仓库样本。两组都显示软件许可证仍然常见；模型专用条款在调用量头部里占了 30%。

这组对照把问题带到了条款范围：同样写着 Apache-2.0，用在软件仓库和模型仓库里，实际覆盖的材料一样吗？

## 19｜Apache-2.0 与 OpenMDW-1.1 怎样约束分发（22:35—24:10）

[画面：两条分发路径尚未展开。]

这一页直接看两份许可证要求下游怎样交付。

[下一步，Apache-2.0 路径出现。]

Apache-2.0 允许分发 Source、Object 和 Derivative Works，也就是说它并不要求二进制分发时同时交出源码。真正触发的是一套分发手续：附许可证，修改过的文件要显著标明，保留相关声明；原作品带有 NOTICE 时，还要传递其中适用的内容。

它的专利许可来自各位 contributor，范围限定在其贡献所必然涉及的专利权利要求。因相关 Work 或 Contribution 发起专利诉讼时，终止的是专利许可。

[下一步，OpenMDW-1.1 路径出现。]

OpenMDW 把模型架构、参数，以及实际置于这份许可下的数据、代码和文档合称 Model Materials。它明示覆盖版权、专利、数据库权利和商业秘密权利。分发清单更短：附许可证，保留适用的版权和来源声明；没有修改文件标记和 NOTICE 机制。

它的诉讼终止范围更大。针对 Model Materials 发起专利或版权侵权诉讼时，全部授权终止，防御性应诉除外。生成输出的边界也写得很直接：OpenMDW 不给输出附加使用、修改或分享义务。

两份许可证都允许商业使用，也都没有 share-alike。它们不会要求发布者补齐没有交付的训练代码和数据。

来源：[Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0.html)、[OpenMDW 1.1](https://openmdw.ai/license/1-1/) 与 [OpenMDW FAQ](https://openmdw.ai/faq/)。

## 20｜许可证给权利，材料决定研究能走多远（24:10—25:30）

[画面：标题。]

经过刚才的分发对照，再把开放模型检查分成两个问题。

[下一步，Rights 出现。]

第一个问题是 Rights：法律上可以做什么？Apache-2.0 和 OpenMDW 都允许使用、修改和分发，分发手续、诉讼终止和输出边界需要按各自文本执行。

OpenMDW 没有定义一套“衍生模型”分类。微调 checkpoint、adapter 和蒸馏模型怎样适用条款，仍要看下游实际分发了哪些 Model Materials。它明确处理的是另一件事：生成输出不承接 OpenMDW 的义务。

[下一步，Materials 出现。]

第二个问题是 Materials：实际上拿到了什么？OSAID 1.0 讨论 Open Source AI 所需的 Use、Study、Modify、Share 自由，以及为修改系统提供 preferred form。Model Openness Framework 把模型组件拆成一组可核验材料。

这几类文件作用不同。许可证授予权利，定义划出边界，开放度框架检查交付完整度。把它们放在一起，才能看清一个模型发布到底开放到了哪一步。

[下一步。]

## 21｜一份模型发布，到底交付了什么（25:30—27:00）

[画面：只有“模型权重”勾选，状态为“只有权重，可下载”。]

这页把材料完整度做成一个简单演示。六项等权，只用来表示材料是否出现，不是官方评分，也不做法律判断。六项材料参考 Model Openness Framework、OSAID，以及常见模型卡和发布实践。

现在只有模型权重。它至少可以下载和运行，但我们还不知道结构、训练过程和评测条件。

[下一步，架构说明勾选。]

补上架构说明以后，模型更容易被理解。研究者可以知道组件怎样连接、输入输出是什么、推理时需要哪些条件。

[下一步，训练代码与数据来源勾选。]

再补训练代码和数据来源，研究入口明显增加。这里的“数据来源说明”并不等于公开全部训练数据；它至少要交代数据构成、处理方式、已知限制和不可发布的原因。否则很多结果仍然无法复核。

[下一步，评测方法与修改文档勾选。]

最后补上评测方法和修改文档，社区才更容易判断改动有没有真的改善，也知道怎样微调、量化、适配和再发布。

现实发布不会整齐地按四步推进，不同模型还会有安全、隐私和第三方权利约束。这页只想留下一个实用的检查习惯：先看条款给了什么权利，再逐项看交付了什么材料。

## 22｜陌生贡献怎样变成长期信任（27:00—29:20）

[画面：第一步“发现入口”。]

最后回到 Community。

一个开放生态要让陌生人有机会进入。第一步是发现入口。软件项目会公开 issue、roadmap 和文档任务；模型项目还可以公开模型卡缺口、数据说明、评测任务和复现实验。入口越具体，第一次贡献的成本越低。

[下一步，切到“提出变更”。]

第二步是提出变更。贡献者把问题、方案和证据写在社区看得见的地方。公开上下文很重要，因为后来者可以接着讨论，维护者也不用在多个私聊里重复解释。

[下一步，切到“公开审查”。]

第三步是公开审查。Review 会找 bug，也会记录技术选择、异议和取舍。对模型项目来说，review 的对象还会包括数据说明、评测条件、权重来源和许可证边界。过程留下来，社区才能回看当时为什么这样决定。

[下一步，切到“共同交付”。]

第四步是共同交付。代码、模型、文档和评测进入 release 以后，社区要长期承担兼容、安全和维护责任。发布是一份承诺，所以 release 不能只剩一个上传动作。

[下一步，切到“积累信任”。]

第五步是积累信任。Apache 里的 committer 和 member 身份来自持续、可见、能够被社区检验的贡献。雇主、头衔和一次性的热度不会自动变成治理权。

这套路径很慢，却很可靠。它把陌生贡献逐步变成共同维护，再把共同维护变成治理责任。CommunityOverCode 的价值，就体现在这些每天都会发生的具体动作里。

[下一步。]

## 23｜结尾（29:20—30:00）

[画面：Community >>> Code。语速放慢。]

回头看今天的四张图，项目和分类还会继续变化。协议可能合并，推理系统还会拆分，新的模型路线也会出现。

开放生态能留下来的，是一套可重复的协作机制：入口能被找到，过程经得起回看，信任跟着贡献增长。

过去这套机制主要覆盖代码。现在，它还要覆盖模型、数据、评测和运行环境。

老规矩继续有效，只是我们需要把它做得更完整。

这就是我对 Community 大于 Code 的理解。
